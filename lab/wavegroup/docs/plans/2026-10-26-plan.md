# wavegroup plan (2026-10-26)

Thesis: Mojo already is a GPU compiler, so a Llama engine that beats tinygrad on the 7900 XTX fits in under 420
lines: kernels are comptime-parametric Mojo, fusion is comptime composition of closures, and wavegroup is only the
graph, the memory planner and the launcher. tinygrad needs ~20k lines of Python because Python cannot emit fast code.

```
gguf (mmap) -> graph (flat SoA arrays) -> plan (fuse, liveness, one arena) -> launch list -> runtime
                                                                               M1: MAX DeviceContext
                                                                               M5: own KFD rings, only if measured
```

## Numbers to beat (tinygrad fork, ~/Brain/tinygrad/2026-10-23-amd-gemm-rating.md)

- fp16 GEMM 4096^3: our Mojo WMMA 113.3 TFLOPS; tinygrad default 60.3.
- Llama 3.2 1B fp16 prefill T=512: tinygrad TinyJit 344.5 ms; our GEMM inside tinygrad TinyJit 36.9 ms.
- Decode: not measured. M4 measures tinygrad and llama.cpp (ROCm) on the same model and prompt.

## Memory: bytes are budget

- One VRAM arena per model. The planner gives each intermediate an offset by liveness (interval colouring): no
  run-time allocator, no frees. Print peak arena bytes vs the sum of all tensors.
- Weights stay q4_K / q6_K / f16 as in the gguf and are dequantised inside the GEMV/GEMM tile, never copied out as fp16.
- gguf is mmapped; the upload streams from the map with no host copy.
- Graph is a struct of arrays of u32 (op, src0, src1, shape id, dtype): no node objects, no pointers.
- KV cache: one fp16 slice per layer, preallocated for max context at load.
- A commit that changes a layout quotes bytes before and after.

## Rules

- Oracles are naive Mojo kernels, not numpy.
- Every GPU run and every Mojo build goes through `gpu-wait run --timeout`.
- Benchmarks: warm median over >= 100 launches on the device timer; cold numbers reported apart.
- No tinygrad code copied. tinygrad is the baseline and a reference to read.

## Risks, each with the check that settles it

- DeviceContext launch overhead on AMD is unknown: M1 prints empty-kernel launches/s; it decides M5.
- Nightly API churn (UnsafePointer already deprecated): the pin holds until a milestone needs a newer nightly.
- The tinygrad prefill hang may be KFD or firmware and follow us: M1's 300 back-to-back launches (tinygrad's default died at 139).
