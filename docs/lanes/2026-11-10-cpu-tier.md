# Lane plan: CPU tier (item `cpu-tier`, dispatched 2026-11-10)

**About 510 new lines make mojo-baro decode the dense 9B on any x86_64 or aarch64 Linux host with no
GPU, byte-identical per op to the GPU m=1 kernels.** `docs/PLATFORM-PLAN.md` prices a CPU backend at
about 10k LOC; that figure is llama.cpp's CPU speed with every quant and SIMD path. This lane buys
compatibility, not speed: one portable path, the `mojo` package alone, no `max`, no ROCm, no Rust.

Status: DISPATCHED 2026-11-10 to one lane, item `cpu-tier` (model opus[1m], effort high, worktree
`../mojo-baro-lanes/cpu-tier`, branch `lane-cpu-tier`). Nothing here was run when it was written. Design source: `docs/design/CPU-BACKEND.md` (2026-10-07, about
1,050 LOC). This plan is that design minus what landed since.

## Steps, each one commit with its byte test first

1. **SSM step and FFN ops.** Extend `kernels/test_cpu_layer.mojo`: every stage compared on the GPU's
   own input for that op, 0 mismatches, planted mutant fails. An op that cannot be made byte-exact
   is reported with its mismatch count; the engine gate then moves to agreement with a same-arm
   control and a bar set before the run.
2. **Pack.** `cpu/pack.mojo` returns the same bytes as the GPU loader for 5 named tensors (sha256).
3. **Engine loop, one thread.** First token of 3 prompts equals the GPU engine. Zero allocations in
   the token loop; `VmRSS` and `VmHWM` printed at ready and at done.
4. **Thread pool.** Same ids as step 3; tok/s and RSS before and after in the commit body.
5. **Engine gate.** `bench/check-cpu-engine.sh`: 20 prompts, forced agreement against the GPU
   engine's greedy ids. Prediction frozen in this file before the run (below).
6. **User path.** `baro-front ENGINE_CPU PACK`, one chat over `curl`, on a host with no GPU driver
   loaded. This is the first claim a user meets; nothing before it is "works".

## Prediction (frozen before step 5; a miss means find the limiter, not drop the tier)

- Agreement: 100% on 20 of 20 prompts, because every op is byte-tested (confidence 60%; the
  megakernel's rmsnorm sites and the SSM scan order are the two places a reorder can hide).
- Speed: bound = pack bytes read per token over DRAM bandwidth. The lane measures the bandwidth of
  this host first (`bench/cpu-gemv.mojo`) and writes the predicted tok/s here before the engine runs.
- Memory: RSS above the page cache under 1 GB at `BARO_TMAX=16384` with f32 KV, stated not measured.

## Rules for the lane

- Boss pane: a lane pane. A QUESTION, BLOCKED or DONE goes there with `herd tell`. No subagents, no forks.
- The report `exchange/lane-cpu-tier-report.md` carries: VERDICT, skills read (path and how far), a table
  step / commit / test / mismatches / LOC per file, the frozen prediction against the result, and what
  no run exercised. READY counts only for a committed sha with a clean worktree.
- No lane preflight and no `run-tests.sh`: the boss runs one of each on the merged tree. The lane runs
  its own gates only. A GPU parity run is `gpu-wait run --timeout 600 --shared --vram 9 -- ...`; an engine
  gate runs alone (no `--shared`).
- Three repairs of the same failure, then BLOCKED with the receipt. A blocked lane reports, never idles.

- Owns: `cpu/**`, `kernels/test_cpu_layer.mojo`, `bench/check-cpu-engine.sh`, `bench/cpu-parity-protocol.md`,
  one line each in `run-tests.sh` and `tools/ci-checks.sh`. Reads everything, edits nothing else.
- Reuse search before the first `def` (an `index.txt` parser and a q8 dot may exist under `serve/`
  or `tools/`): name what was found, or say none in one line.
- Kernel files stay untouched. A needed kernel change is a QUESTION.
- Every build under `systemd-run --user --scope -q -p CPUQuota=150% -p MemoryMax=10G -p MemorySwapMax=0`;
  read Tctl first, wait at 84 C or more. GPU runs only through `gpu-wait`, alone on the card.
- Floors: `BARO_TMAX >= 16384`, `max_tokens` cap >= 16000. The forced-agreement gate sends 64 forced ids
  per prompt under that cap.
- LOC is the budget: the report lists lines per file against the table above; a file over its row
  explains why. Shorter code that passes the same test replaces the longer.
- Commits by pathspec, no author trailer, `hot path / before / after / input` in the body.
- Skills, read before the first edit (the report states how far each was read):
  `~/Brain/Skills/own/mojo-baro/SKILL.md`, `~/Brain/Skills/own/mojo-lean/SKILL.md`,
  `~/Projects/mojo/.claude/skills/mojo-syntax/SKILL.md`, `~/Brain/Skills/own/memory-optimization/SKILL.md`
  with `references/mojo.md` and `references/parallelism.md`, `~/Brain/Skills/own/gpu-kernels/SKILL.md`
  (parity section only), `~/Brain/Skills/own/bench-gates/SKILL.md` (gate authoring, preregistration).

## Decisions

1. Model: opus[1m], effort high (owner, 2026-11-10).
2. K-quant on CPU stays OUT of this lane (default; +150 as its own lane after the engine gate).
4. No q8 row dot in this lane (lane QUESTION, 2026-11-10, default accepted): `engine-pack-q4` holds 257 q4,
   184 f32 and 1 bf16 tensors and no q8 tensor, so no test could exercise it. It joins the q8-pack lane.
5. One kernel line is allowed (lane QUESTION, 2026-11-10): `kernels/ssm.mojo` imports `rsqrt` from `bexp`
   as `attn.mojo` and `elementwise.mojo` do, so the SSM conv scale is byte-equal on CPU under
   `-D BARO_SHARED_EXP=1`. Condition: `isa-diff` shows identical ISA for the default build, else it does
   not land.
6. Scope of the parity claim, corrected: the CPU path equals a GPU build with `-D BARO_SHARED_EXP=1` on the
   launch path. `kernels/mega.mojo` imports the std math directly, so the megakernel (the default decode
   path) is outside the claim. The step 5 reference engine is built with that define and run with
   `BARO_MEGA=0`, both read back from its log.
3. Step 6 host, default: this machine with the GPU hidden from the process (no `max` in the import
   graph, so the binary cannot open the device); a second physical host is OPEN and is a QUESTION to the
   boss pane when step 5 passes.

## What this does not show

The 510 is an estimate from the design's table and a line count of what exists; no new file was
written. The CPU tier makes the engine run on more machines for the model families it already has.
It does not add model coverage: llama.cpp runs hundreds of architectures, this engine runs four.
