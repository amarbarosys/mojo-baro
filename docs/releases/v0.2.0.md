## What it does

<!-- Stable description of the program. Carried forward from the previous note; edit only when the product itself changes.
     3 to 6 lines: what it is, who uses it, where it runs (URL/port/binary), how to start it. -->
An LLM inference engine for AMD RDNA3 GPUs, with every GPU kernel written in
[Mojo](https://www.modular.com/mojo). It serves chat over an OpenAI-compatible
HTTP API on a single RX 7900 XTX. On matched weights it decodes ahead of
llama.cpp on the dense 9B (Q4_0) and level with it on the 35B MoE; on q8 and
on packs built from Q4_K_M it is still behind.

The point of the project is the kernels. Consumer RDNA3 cards are where most
people actually have 24 GB of VRAM, and they are not what the vendor libraries
are tuned for. This repo measures how much of that gap is real, one
preregistered round at a time.

**Have an AMD GPU that isn't a 7900 XTX?** Your card is the most useful thing
you can contribute. See [docs/amd-family.md](docs/amd-family.md): fifteen
minutes, no model weights needed.

## Highlights

- **Own state codec, three tiers.** A 32k checkpoint that shipped as 585 MB (BAROST03) now
  ships as 184 MB (BAROKV6) and is usable 0.40 s after the transfer starts on 10 GbE instead
  of 0.78 s, with the same teacher-forced agreement as the int8 pool (mean 99.5%, min 96.9%).
- The int8-KV engine (`--kvq int8`) loads BAROKV4 / BAROKV5 / BAROKV6 payloads directly; the
  4-bit rows, f16 scales and rANS streams are expanded by GPU kernels, byte-identical to the
  host reconstruction on every gate.
- The load stage pins 0.60 GB instead of 0.88 GB of host memory at TMAX 32768.

## Changes

### Added
- `tools/kvc_int4.py`: BAROST03 -> BAROKV4 (4-bit rows, 1.81x) or `--kv5` (f16 conv, SSM
  and row scales, 2.00x). `tools/kvc_rans.py`: BAROKV5 -> BAROKV6 (rANS streams, 3.19x),
  with a Python oracle decode (`--check N`).
- `kernels/state.mojo`: `amar_kv4_unpack[T16]` and `amar_kv6_decode`.
- `bench/kvc-agree.sh` (forced-agreement quality gate for a reconstruction),
  `bench/kvc-bytes.sh` (device path byte-exact against the reconstruction),
  `bench/c19-ttft.sh` `C19_KV4=<payload>` arm.
### Changed
- `load_state` on the int8 engine accepts magics `BAROKV4\0`, `BAROKV5\0`, `BAROKV6\0`
  beside BAROST03; the f32 engine refuses them with a named error. `state_hot` accepts them.
- `LoadStage`: payload halves stage in the existing K/V host buffers (no third pinned slab).

## Known limits

- The packers are Python (numpy); encoding a 32k state takes about 35 s on the CPU. The engine
  does not write BAROKV* files: `save_state` still writes BAROST03 (or BAROST02 on f32).
- BAROKV4/5/6 are int8-pool payloads: only the `--kvq int8` engine loads them.
- 32k checkpoints and curl: fixed after the tag (`X-Baro-Meta` slimmed, `GET /v1/checkpoints/ID/meta` added); the tag's binary still sends the 142 KB header.

## Upgrade / run

<!-- Exact commands. Migrations, new deps, service restarts, config keys. "None" if nothing changed. -->
```
# int8-KV engine, then a payload from a BAROST03 checkpoint
tools/baro build --kvq int8
python3 tools/kvc_int4.py STATE.baro kv5.payload recon.baro --kv5
python3 tools/kvc_rans.py kv5.payload kv6.payload --check 32
# load it like any state file: {"state_load": "kv6.payload", ...} over the engine protocol
```
