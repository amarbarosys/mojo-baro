## What it does

<!-- Stable description of the program. Carried forward from the previous note; edit only when the product itself changes.
     3 to 6 lines: what it is, who uses it, where it runs (URL/port/binary), how to start it. -->
An LLM inference engine for AMD RDNA3 GPUs with every GPU kernel written in Mojo. It serves chat over an
OpenAI-compatible HTTP API on one RX 7900 XTX (`tools/baro serve MODEL.gguf`, default port 8080), from
self-describing GGUF bakes that carry their own kernel sources.

## Highlights

- Bakes now build their weight pack with the Mojo engine packer: 1.2 to 2.5 times faster and at most 0.96 GB peak
  memory, where the Python packer peaked at up to 12.3 GB. The packs are byte-identical.

## Changes

### Added
- `tools/engine-pack.mojo`: the qwen35 trunk (`--q8`, `--q4`, `--q4-draft`, bf16), `--dense` and `--arch qwen35moe`
  packs plus `identity.json`, byte-identical to `tools/engine-pack.py`, which stays as its oracle (`3708cc2`).
- `tools/engine-pack-check.sh` and `tools/engine-pack-fixture.py`, the byte check against the oracle (`3708cc2`).
### Changed
- `tools/bake.sh` embeds the Mojo engine packer by default; `tools/baro serve` and `tools/baro run` build every pack
  with the bake's own tool through `tools/pack-run.sh` (`3708cc2`).
- Mojo pack tools are built strict IEEE (`--fp-mode contract=off`) (`1b1a46b`).

## Known limits

- The ternary packs (`--q2b3`, `--tq1`, `--tq2`) are still built by `tools/engine-pack.py`; the Mojo tool refuses
  them and says so.
- The Mojo packer dequantises F32, F16, BF16, Q4_0, Q8_0, Q4_K, Q5_K and Q6_K sources; any other type stops with an
  error naming it (`--arch qwen35moe` copies other types as they are and only dequantises `output.weight`).
- Only the Llama-1B bake was re-baked and served end to end; the other five models were checked at the pack level.
- Timings are with the GGUF in page cache for both tools.
