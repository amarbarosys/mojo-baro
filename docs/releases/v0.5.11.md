## What it does

<!-- Stable description of the program. Carried forward from the previous note; edit only when the product itself changes.
     3 to 6 lines: what it is, who uses it, where it runs (URL/port/binary), how to start it. -->
An LLM inference engine for AMD RDNA3 GPUs with every GPU kernel written in Mojo. It serves chat over an
OpenAI-compatible HTTP API on one RX 7900 XTX (`tools/baro serve MODEL.gguf`, default port 8080), from
self-describing GGUF bakes that carry their own kernel sources.

## Highlights

<!-- 1 to 5 bullets a user would notice. Lead with the benefit, not the implementation. -->
- The Qwen3.8-Flash-Next engine answers over HTTP now: `baro-serve` drives `serve/q4x.mojo` (`BARO_SERVE=1`), a 16000-token
  generation streams from `/v1/completions` with the same ids as the stdin mode, and `POST /v1/cancel` stops it.
- Long context is fast: decoding at a 16384-token context went from 77.9 to 27.4 ms/token (same ids), and a 16000-token
  generation from 48.1 to 20.2 ms/token on average.
- 16K runs work on the 24 GB card with `Q4X_CHUNK=8192`; agreement with llama.cpp at a 16384-token prompt reads 96.88%, equal to the
  llama.cpp CPU control.

## Changes

### Added
- `BARO_SERVE=1 BARO_PACK=FIRST_SHARD` on `serve/q4x.mojo`: baro-serve line protocol, stop sequences, per-token cancel, greedy only
  (`4227a1a`).
- `Q4X_ATTSPLIT=N` (default 512, 0 = off): decode attention as three byte-exact kernels (`ba3594c`).
- `bench/q4x-ab.sh` (same-job A B B A, resident), `bench/q4x-trace.sh` + `tools/q4x-trace-gaps.py` (rocprofv3 busy/idle split),
  `bench/q4x-prompts-16k`, the 16K mode of `bench/q4x-gate.sh`, an HTTP arm in `bench/q4x-serve-check.sh`.
### Changed
- `bench/q4x-gate.sh` refuses a window under 16384 (`bench/min16k.sh`).

## Known limits

<!-- Honest list: slow paths, unsupported cases, flaky upstreams, anything UNVERIFIED. -->
- HTTP serves greedy tokens only; temperature, penalties, logprobs, hidden, embed and state_save/load answer an error line.
- A one-forward 16384-token prefill does not fit well: it spilled 12 to 16 GB to GTT and faulted once. Use `Q4X_CHUNK=8192`.
- Transient GTT peaks of 15.2 and 4.2 GB in 2 of 6 chunked runs, no throughput change, cause not found.
- The 16K A/B has 2 prompts, not 20 (2 minutes of prefill each); the 20-prompt medians are at short context.
- Short-context decode is unchanged at about 20 ms/token; launch gaps and host waits after the router remain.
